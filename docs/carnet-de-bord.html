Vue d’ensemble

Memora est un monorepo : une seule base de code réunit l’API, le client web, l’application mobile et les paquets partagés. C’est le premier écart avec MSBACK et MSFRONT, qui vivaient dans deux dépôts séparés.

Pourquoi un monorepoAvec deux dépôts, le contrat entre le client et le serveur est recopié à la main des deux côtés, et il dérive silencieusement. Ici, les types et les schémas de validation vivent dans packages/types : le client ne peut plus appeler une route avec une charge utile invalide sans que la compilation échoue.
memora/ ├── apps/api/ l'interface de programmation │ ├── prisma/schema/ un fichier par modele │ └── src/ │ ├── server.ts demarrage, Socket.io, arret propre │ ├── app.ts construction Express, exportee pour les tests │ ├── router.ts assemble les features sous /api │ ├── config/ env, prisma, redis, storage │ ├── middlewares/ validate, requireAuth, rateLimiter, errorHandler │ ├── utils/ errors, jwt, hash, slug │ └── features/ │ ├── auth/ routes, controleur, service, tests │ └── events/ └── packages/types/ enums et schemas Zod partages
À retenir pour l’oral. L’arborescence suit le métier, les responsabilités suivent les couches. Dans chaque dossier de features/ on retrouve la même chaîne : route → contrôleur → service → accès aux données. La compétence 6 du référentiel parle d’application organisée en couches : elles sont bien là, simplement regroupées par domaine.
Lot 1

Le socle

Les fichiers de configuration du dépôt. Aucun code métier, mais ce sont eux qui déterminent la rigueur de tout le reste.

configpnpm-workspace.yaml

Déclare que le dépôt contient plusieurs paquets : tout ce qui se trouve dans apps/ et packages/. C’est ce fichier qui remplace tes deux dépôts séparés.

configturbo.json

Décrit les tâches et leurs dépendances.

"type-check": { "dependsOn": ["^build"] }

Le circonflexe signifie « les dépendances de ce paquet ». Avant de vérifier les types de l’API, Turbo compile donc d’abord @memora/types. Sans cette ligne, l’API pourrait être vérifiée contre une version périmée des contrats.

configtsconfig.base.json

Le TypeScript strict pour tout le dépôt. Trois options vont plus loin que le strict par défaut :

noUncheckedIndexedAccesstableau[0] est typé T | undefined, ce qui oblige à vérifier avant d’utiliser. C’est la source d’erreur numéro un en production.
exactOptionalPropertyTypesDistingue « propriété absente » de « propriété présente valant undefined », deux choses que Prisma traite différemment.
verbatimModuleSyntaxImpose import type quand on n’importe qu’un type. Les imports de types disparaîssent alors complètement du code compilé.
infradocker-compose.yml

PostgreSQL 16, Redis 7.4 et MinIO, avec les images exactes de la production.

Le détail qui compteRedis tourne avec --appendonly yes. Sans cette option, un redémarrage viderait les compteurs de poses — en pleine soirée, tous les invités récupéreraient un quota neuf.
métierpackages/types/src/enums.ts

Les valeurs métier et les bornes chiffrées, déclarées une seule fois : types d’événement, états, modes d’aperçu, portées de publication, rôles. Puis le quota entre 5 et 60, 24 par défaut, 200 invités maximum, 30 jours de rétention, 3 poses bonus, fenêtre de 10 minutes.

export const EVENT_STATES = ['DRAFT','OPEN','CLOSED','PUBLISHED','PURGED'] as const;
export type EventState = (typeof EVENT_STATES)[number];

Le as const fige le tableau, et l’indexation par [number] en dérive le type union. Résultat : une seule source, un tableau utilisable à l’exécution et un type vérifié à la compilation.

métierpackages/types/src/schemas.ts

Le contrat de chaque route, écrit avec Zod. Le serveur valide ce qu’il reçoit, le client valide avant d’envoyer, avec les mêmes schémas.

closesAt: z.coerce.date().refine((d) => d.getTime() > Date.now(), {
  message: "L'heure de fermeture doit etre posterieure a maintenant",
}),
Ce que fait z.inferLe type TypeScript est dérivé du schéma, pas écrit à côté. Modifier une règle de validation modifie le type au même instant : ils ne peuvent pas diverger.
donnéesprisma/schema/ — huit fichiers

Un fichier par modèle, assemblés automatiquement grâce à "prisma": { "schema": "./prisma/schema" } dans le package.json. Les enums sont placés dans le fichier du modèle auquel ils appartiennent.

Les noms passent en anglais, les commentaires restent en français. La correspondance avec le MCD du dossier : EVENEMENT devient Event, PELLICULE devient Roll, TABLE_SALLE devient EventTable, DEMANDE_RETRAIT devient RemovalRequest.

Trois contraintes qui portent des règles métier@@unique([eventId, deviceToken]) sur Roll interdit à un même appareil d’ouvrir deux pellicules sur le même événement. @unique sur idempotencyKey rend le rejeu impossible au niveau de la base, pas seulement du code. @unique sur externalRef empêche qu’une notification Stripe reçue deux fois crédite l’événement deux fois.

Roll représente un appareil pour un événement, pas une personne. C’est la traduction exacte du choix d’identification par appareil décrit dans le dossier.

Lot 2

Configuration

Quatre fichiers transverses, dont aucun ne contient de règle métier, mais dont deux portent des garanties techniques déterminantes.

configconfig/env.ts

Valide toutes les variables d’environnement au démarrage avec Zod, et arrête le processus si l’une manque.

L’écart avec MSBACKUn simple dotenv.config() laisse découvrir qu’une variable est absente au premier appel qui en a besoin, souvent en production. Ici, le serveur refuse de démarrer, avec la liste des champs fautifs.
configconfig/prisma.ts

Instance unique, mise en cache sur globalThis en développement.

Pourquoi ce cachetsx watch recharge les modules à chaque sauvegarde. Sans lui, chaque sauvegarde ouvrirait une connexion supplémentaire jusqu’à saturer PostgreSQL.
cléconfig/redis.ts

La connexion Redis, et le script dont dépend toute la garantie de quota.

local left = tonumber(redis.call('GET', KEYS[1]) or '0')
if left <= 0 then return -1 end
return redis.call('DECR', KEYS[1])
Pourquoi un script Lua et pas deux commandesRedis exécute un script d’un seul tenant : aucune autre commande ne peut s’intercaler. Une séquence GET puis DECR laisserait deux requêtes simultanées lire la même valeur avant qu’aucune n’ait écrit, et le quota deviendrait négatif. C’est exactement l’anomalie racontée dans le dossier au sprint 4.
cléconfig/storage.ts

Ne sert qu’à signer des adresses. signUpload en produit une valable 5 minutes pour déposer, signRead une valable 15 minutes pour consulter.

Le principe à savoir expliquerLe fichier ne transite jamais par l’API. Celle-ci autorise, puis elle constate. Trois conséquences : le processus applicatif ne sature pas pendant un pic de déclenchements, la mémoire du serveur reste stable, et l’API n’expose aucune surface de traitement de contenu binaire.

forcePathStyle: true est obligatoire avec MinIO, dont les adresses sont de la forme host/bucket/objet et non bucket.host/objet.

Lot 3

Fondations transverses

Les utilitaires et les middlewares dont toutes les features dépendent.

utilsutils/errors.ts

AppError et ses sous-classes typées, chacune portant son code métier et son statut HTTP : QuotaExhaustedError, ConsentRequiredError, EventClosedError, EventFullError, UnauthorizedError, ForbiddenError, NotFoundError.

Tout ce qui n’hérite pas d’AppError est traité comme une erreur interne dont la cause ne sort jamais du serveur.

sécuritéutils/jwt.ts

Trois sortes de jetons : accès (15 minutes), renouvellement (30 jours), et le jeton d’appareil de l’invité.

Le détail à remarquerverifyDeviceToken renvoie null au lieu de lever une exception. Un cookie invalide n’est pas une erreur : on ouvre simplement une nouvelle pellicule, comme pour un appareil qui arrive pour la première fois.
sécuritémiddlewares/requireAuth.ts

Vérifie le jeton, puis recharge l’utilisateur depuis la base au lieu de faire confiance au contenu du jeton — exactement comme ton authMiddleware.js de MSBACK.

Pourquoi rechargerUn compte supprimé, ou dont le rôle a changé, ne doit pas continuer à passer parce qu’il détient un jeton émis quinze minutes plus tôt.

requireRole('ADMIN') se chaîne après requireAuth pour restreindre une route.

utilsmiddlewares/validate.ts

Applique un schéma Zod au corps de la requête avant le contrôleur. Celui-ci reçoit donc des données déjà validées et déjà typées : il n’a plus rien à vérifier.

utilsmiddlewares/errorHandler.ts

Attribue un identifiant de corrélation à chaque incident, le journalise, et le renvoie au client. Quand un utilisateur signale un problème avec cet identifiant, on retrouve la ligne exacte du journal.

Trois cas : erreur de validation Zod (422 avec le détail des champs), erreur applicative prévue (son statut et son message), et tout le reste (500, cause gardée au serveur).

utilsutils/slug.ts

Fabrique l’identifiant public d’un événement : partie lisible plus suffixe aléatoire.

mariage-de-lea-et-sam-7f3a9c
Pourquoi le suffixeSans lui, l’adresse d’un mariage serait devinable à partir des prénoms des mariés, et n’importe qui pourrait rejoindre l’événement sans avoir jamais vu le QR code.
Lot 4

Authentification

Première feature complète. Quatre fichiers dans features/auth/.

métierauth.service.ts

Les règles, sans connaître Express. Le service reçoit des données et renvoie des données, ce qui le rend testable seul.

const hash = user?.passwordHash ?? '$2b$12$invalid...';
const valid = await verifyPassword(password, hash);
if (!user || !valid) throw new UnauthorizedError('Identifiants incorrects');
Le point le plus important de ce fichierQuand le compte n’existe pas, on appelle quand même verifyPassword sur une empreinte factice. Sans cela, la réponse serait plus rapide pour une adresse inconnue, et ce simple écart de temps permettrait d’énumérer les comptes. C’est une défense contre une attaque temporelle.
sécuritéauth.controller.ts

Traduit HTTP : lire, appeler le service, poser le cookie, choisir le statut. Les erreurs partent vers l’intercepteur par next(err).

httpOnly: true,             // inaccessible au JavaScript de la page
secure: isProduction,       // uniquement en HTTPS en production
sameSite: 'strict',         // jamais envoye depuis un autre site
path: '/api/auth/refresh',  // et seulement sur cette route
Pourquoi c’est une défense CSRFLe jeton d’accès voyage dans l’en-tête Authorization, que le navigateur n’ajoute jamais de lui-même. Une requête forgée depuis un autre site part donc sans jeton. Le seul cookie utilisé porte SameSite=Strict et n’est accepté que sur la route de renouvellement.
testsauth.service.test.ts

Prisma est remplacé par un double : ces tests portent sur la règle métier, pas sur la base.

Le test qui compte vérifie que la réponse est rigoureusement identique selon que le compte existe ou non : même code, même message. C’est une propriété de sécurité, pas une propriété fonctionnelle.

Lot 5

Événements

Création, configuration, ouverture, fermeture, tables de salle. Douze tests.

métierevent.service.ts

Cinq règles portent tout le module.

assertCanManageLa matrice des rôles du dossier, appliquée côté serveur. Elle distingue l’hôte du co-hôte en renvoyant isOwner, ce qui permet ensuite de réserver certaines actions au seul propriétaire.
Réglages figés à l’ouvertureLe quota, le mode d’aperçu et le type ne sont plus modifiables une fois l’événement ouvert. Changer le quota en pleine soirée créerait une inégalité entre les invités déjà arrivés et les suivants.
Offre gratuiteLe premier événement d’un compte est bridé à dix poses. openEvent est le seul point de contrôle du paiement, et il refuse qu’un co-hôte ouvre l’événement.
testsevent.service.test.ts

Douze tests : droits de l’hôte, du co-hôte et d’un étranger ; bridage du premier événement ; exigence de paiement au deuxième ; verrouillage du quota après ouverture ; couleur toujours modifiable ; transitions d’état refusées.

Un test qui va plus loinCelui de l’ouverture gratuite vérifie en plus qu’aucune requête de paiement n’a été faite. Il ne se contente pas de constater que ça passe : il vérifie que ça passe pour la bonne raison.

Concepts à maîtriser

Les cinq notions sur lesquelles le jury peut creuser, avec la formulation courte à connaître.

notionAtomicité

Une opération atomique s’exécute entièrement ou pas du tout, sans qu’aucune autre opération puisse s’intercaler au milieu.

Dans Memora : le script Lua qui décrémente le quota. Deux déclenchements simultanés ne peuvent pas lire la même valeur avant d’écrire.

notionIdempotence

Une opération idempotente produit le même résultat qu’elle soit exécutée une ou plusieurs fois.

Dans Memora : le client génère une clé UUID par prise de vue. Un rejeu retrouve la photographie existante au lieu d’en créer une seconde. La contrainte @unique en base garantit la propriété même si le code se trompe.

notionAdresse signée

Une adresse temporaire, signée cryptographiquement, qui autorise une opération précise sur un objet précis pendant une durée limitée.

Dans Memora : 5 minutes pour déposer, 15 minutes pour lire. Le seau MinIO n’est jamais public.

notionJeton d’accès et jeton de renouvellement

Le jeton d’accès est court (15 minutes) et voyage dans l’en-tête. Le jeton de renouvellement est long (30 jours) et reste dans un cookie inaccessible au script.

Pourquoi deux : un jeton d’accès volé n’est exploitable que quinze minutes, et le jeton long ne peut pas être lu par du JavaScript injecté.

notionMinimisation des données

Principe du RGPD : ne collecter que ce qui est nécessaire à la finalité.

Dans Memora : aucune adresse électronique ni compte pour l’invité, prénom facultatif, et les coordonnées GPS retirées avant que le fichier ne quitte le téléphone. Retirer avant l’envoi, ce n’est pas la même chose que supprimer après collecte.

Questions de jury

Questions probables sur ce qui est déjà écrit. Réponds à voix haute avant d’afficher la réponse.

Pourquoi avoir choisi Redis plutôt que PostgreSQL pour compter les poses ?
Lors d’un moment fort, plusieurs dizaines de déclenchements arrivent en quelques secondes sur le même événement. Un UPDATE concurrent sur une seule ligne de PostgreSQL serait un point de contention, avec des attentes de verrou. Un compteur en mémoire, décrémenté par un script atomique, encaisse la charge. La valeur est ensuite reportée en base dans la même transaction que la création de la photographie.
Que se passe-t-il si un invité appuie deux fois très vite sur le déclencheur ?
Deux cas. Si ce sont deux prises de vue distinctes, chacune porte sa propre clé d’idempotence et consomme une pose : c’est le comportement attendu. Si c’est la même requête rejouée — réseau instable, reprise automatique — la clé est identique, le serveur retrouve la photographie déjà créée et ne décrémente pas une seconde fois.
Un invité peut-il contourner son quota ?
Oui, et c’est documenté comme une limite assumée. En navigation privée ou depuis un autre navigateur, il obtient une nouvelle pellicule. Le détecter supposerait une empreinte de navigateur, que la CNIL assimile à un traçage soumis à consentement — ce qui contredirait la démarche de minimisation. Deux garde-fous : le nombre de pellicules est visible par l’hôte, et le plafond de 200 participants borne l’abus.
Pourquoi la photographie ne passe-t-elle pas par l’API ?
Trois raisons. La charge : cent invités envoyant 2 Mo chacun satureraient le processus applicatif. La mémoire : Node devrait tamponner chaque fichier. La sécurité : l’API n’expose aucune surface de traitement de contenu binaire. Elle délivre une adresse signée valable cinq minutes, le navigateur transfère directement, puis confirme.
Comment garantissez-vous qu’une photo n’est pas visible avant publication ?
Le seau de stockage n’est jamais public : aucune adresse n’est exploitable sans signature. La signature n’est délivrée qu’après contrôle des droits côté serveur, en fonction de la portée de publication choisie par l’hôte. Les clés d’objet contiennent un UUID, donc rien n’est devinable. Et l’interface ne décide jamais : elle masque, le serveur autorise.
